# Навигация по шагам работы

Рабочие материалы находятся в папке `материалы проекта/`. Пути вида `дизайн/`, `аналитика/`, `референсы/`, `тексты/` и `tilda-work/` ниже указаны относительно этой папки. Сайт находится уровнем выше, в корне репозитория.

## Как определить текущий шаг

1. Прочитать [состояние проекта](<Состояние проекта.md>) и учесть последнюю просьбу пользователя и доступную переписку. Самостоятельно определить текущий шаг по задаче, завершённым результатам и полученным согласованиям.
2. Если пользователь редактирует инструкции, работать с затронутыми файлами. Изменение правил само по себе не запускает аналитику и не переводит проект на следующий шаг.
3. Если работа над сайтом ещё не начата и пользователь поручает её начать, открыть только инструкцию шага 1. Если шаг уже выполняется или ожидает согласования, оставаться на нём. Следующий шаг открывать для выполнения только после завершения предыдущего и согласия пользователя. До выполнения получить ответ на рекомендацию модели по [правилу выбора модели](<Расход и модели.md>); согласование перехода и модели можно объединить в одном вопросе.
4. Читать только инструкцию выбранного шага, необходимые исходные материалы и ресурсы, на которые она ссылается. Не читать все шаги и соседние инструкции на каждом обращении. При запросе на изменение нескольких шагов открыть только затронутые.
5. Наличие результата в папке не означает согласование. При расхождении состояния с явными указаниями пользователя опираться на переписку и обновить состояние. Если шаг или согласование нельзя установить, задать один конкретный уточняющий вопрос вместо перечитывания всех инструкций.
6. После работы над этапом обновить состояние: текущий шаг, статус, ссылки на результаты, оставшиеся вопросы и полученное согласование. Фиксировать согласие только по реальному ответу пользователя: краткая цитата или точное описание ответа с датой. Не отмечать шаг согласованным заранее.
7. При согласованном переходе открыть следующий шаг по ссылке из корневого `AGENTS.md`. После завершения всех описанных шагов ждать новых указаний пользователя.

## Общие правила

- Работать на русском языке.
- Использовать реальные компании и проверенные открытые источники. При исследовании открывать сайты и страницы, а не делать выводы только по поисковым описаниям.
- К существенным фактам и выводам прикладывать ссылки на источники; фиксировать дату проверки.
- Разделять подтверждённые сведения, аналитические выводы и гипотезы. Не выдавать предположения за ответы клиента.
- Если сведений нет, прямо писать: «Недостаточно информации: …» с пояснением, что именно неизвестно. Недоступный источник не считать доказательством отсутствия информации или функции.
- Сохранять аналитику в `аналитика/`, выжимку для копирайтера и тексты страниц в `тексты/`, описание референсов и проверки дизайна в `дизайн/`, подготовку настроек в `подготовка сайта/`, код секций T123, ID блоков и проверки Tilda в `tilda-work/`. Создавать папки по необходимости на соответствующем этапе; показывать пользователю краткий результат со ссылками на файлы.
- Учитывать уже сделанный выбор и согласования из переписки. Не запрашивать их повторно, если условия не изменились.
- Визуальную основу брать только из материалов, актуальных для нового проекта. Существующий UI kit и Cygre в `референсы/` относятся к прошлому проекту. При работе с визуальным направлением читать [правила референсов](<Референсы.md>).
- Цифры и другие утверждения о бренде использовать только из его подтверждённых материалов или данных пользователя или клиента. Это правило действует для текстов, дизайна, SEO и Tilda.

## Согласование каждого шага

- Выполнять один шаг за раз. После его завершения показать результат пользователю и запросить согласование перед переходом к следующему.
- Начинать следующий шаг только при выполнении обоих условий: предыдущий шаг завершён и пользователь явно согласовал результат и переход. Выбор предложенной ниши или компании считается согласованием соответствующего шага.
- Не начинать заранее исследования, подготовку материалов или другие работы следующего шага, пока согласие не получено.
- Молчание, истечение времени, показ результата или собственный вывод о готовности не считать согласием пользователя. Просьба исправить результат означает продолжение текущего шага.
- Если нужны правки, внести их, показать обновлённый результат и дождаться согласования. Уже полученное согласие повторно не запрашивать.
- В конце каждого шага фиксировать: что завершено, где сохранён результат, что осталось неизвестным и какой шаг предлагается следующим. Допустимые пробелы, явно отмеченные по правилам этапа, не подменять выдуманными данными.
- После последнего описанного шага также показать результат на согласование. Дальнейшие этапы выполнять после добавления их пользователем и получения согласия на переход.

## Как дополнять инструкции

Детали и новые правила записывать в инструкцию соответствующего шага. При добавлении этапа создать отдельный Markdown-файл с номером и названием шага прямо в `Шаги работы/` и добавить ссылку в корневой `AGENTS.md`. В `Шаги работы/` хранить только файлы `.md`, без вложенных папок; общие правила и вспомогательные инструкции также размещать на этом уровне. Результаты работы и другие форматы сохранять в предназначенных для них папках проекта. Общие правила и порядок согласований хранить здесь, фактическое продвижение — в файле состояния. Корневой `AGENTS.md` оставлять списком ссылок.

Сохранять последовательность: исходные условия и ниша → компания → дизайн-система → карта сайта → тексты для сайта → подключение Tilda → первый экран кодом в T123 → весь сайт кодом в блоках T123 → SEO и скорость → юридические элементы → итоговая проверка Tilda → подключение форм. Условия и ответвления читать только в инструкции текущего шага. По указанию пользователя от 28.10.2026 применять [вёрстку кодом в T123](<Вёрстка T123.md>): одна секция сайта — один блок с HTML/CSS/JS, без переноса дизайна в элементы Zero Block. Код проверять и использовать в Tilda без повторной сборки на другом стеке.

Сохранять согласование каждого шага, навыки copywriting, redaktura и infostyle на шаге 5, приоритет лендинга, соответствие дизайна актуальным материалам из `референсы/` и адаптив по ходу разработки, пока пользователь явно не изменит эти условия. Общие правила дизайна читать только при работе над соответствующими шагами по их ссылкам. При корректировке устранять противоречия в затронутых файлах.

При правках сайта применять раздел о точечных изменениях из [правил расхода и моделей](<Расход и модели.md>). Для визуальных материалов использовать сохранённый разбор после проверки актуальности по [правилам референсов](<Референсы.md>), а не перечитывать весь исходник.
